## 开始之前：这份方案在教你什么（先读这段）

你已经会测"页面"了（UI 自动化）。但真实系统里，页面只是冰山露出水面的一角——**水面之下是接口（API）**：前端页面本身不会算账，它把你的请求发给服务器，服务器处理后把数据递回来，页面再展示。这个"递数据"的通道就是接口。

**为什么测接口很重要？** 对比一下：

| | UI 自动化（测页面） | 接口自动化（测通道和逻辑） |
|--|------------------|--------------------------|
| 速度 | 秒级 | 毫秒级 |
| 稳定性 | 相对脆（页面一改版脚本就得修） | 稳（接口不太变） |
| 能发现问题 | "用户看到的东西对不对" | "数据对不对、逻辑对不对"（页面背后的账） |
| 维护成本 | 高 | 低 |

所以业界的分工是：**接口自动化当主力（量大），UI 自动化只保核心路径（量少）**——这正是测试金字塔的形状。

**一个必须先说清的事**：本项目（书香阁）是纯静态网站，**没有接口**可测。怎么办？**Day2 我们花一小时，用 Flask 给图书馆亲手造一个迷你接口**（新增 `api/` 目录，完全不动现有网页）。造接口本身就是极好的学习——见过接口怎么写的，你才知道怎么测它。等你将来遇到真实项目的接口，测试方法一模一样。

# Day 1：自顶向下 —— 什么是接口，接口自动化全景

> **今天的目标**：不写代码。搞懂接口是什么、HTTP 怎么工作、接口用例长什么样，并亲手发一个真实的请求。

## 1.1 什么是接口（30 min）

**餐厅比喻**：你（顾客）不会自己冲进厨房炒菜，你把点菜单递给**服务员**，服务员递给厨房，做好后端出来。服务员就是**接口**——他不做饭，负责**传话**：接收请求、转交处理、返回结果。

软件世界同理：

```
   你看到的页面            页面背后的世界
 ┌─────────────┐       ┌──────────────────────┐
 │  前端（页面） │ ────→ │  接口（传话的服务员）   │
 │  负责好看     │  HTTP │        │              │
 └─────────────┘       ┌────────▼─────────┐    │
                       │  服务器程序 + 数据库 │    │
                       │  负责真正的逻辑和数据 │    │
                       └──────────────────┘    │
```

- 前端（页面）：负责展示，"《活着》这本书显示在这里"
- **接口**：负责传数据，"把全部图书的数据给我" → 返回一堆数据
- 服务器：负责真正的逻辑（能不能借？罚款多少？）和存储

**本项目为什么没有接口？** 因为它是纯静态网站——页面内容直接写死在 HTML 里，没有服务器程序在后面算账。真实项目（比如京东、B 站）都是"前端页面 + 后端接口"分离的，页面上的每个数字、每次点击提交，背后都是接口在传话。

## 1.2 五分钟看懂 HTTP（45 min，今天最重要的基础）

前端和接口之间的"传话"用的是一套全世界统一的规矩，叫 **HTTP**。一次传话 = **一个请求（Request）+ 一个响应（Response）**。

### 请求：我想干什么

一个请求包含三样东西：

| 组成 | 人话 | 例子 |
|------|------|------|
| **方法（Method）** | 动词：想干哪种事 | GET=查、POST=新建/提交、PUT=改、DELETE=删 |
| **网址（URL）** | 找谁 | `http://localhost:5000/api/books/1` |
| **参数/请求体** | 具体内容 | 查询条件，或要提交的数据（如 `{"book_id": 1}`） |

> 记忆口诀：**查用 GET，提交用 POST**。初学者掌握这两个就够了，PUT/DELETE 用到再学。

### 响应：办得怎么样

响应也包含两样东西：

| 组成 | 人话 | 例子 |
|------|------|------|
| **状态码（Status Code）** | 一句话结论 | 200=办成了，404=没这人，500=服务器自己炸了 |
| **响应体（Body）** | 具体内容 | 一段 JSON 数据 |

状态码入门三兄弟（先记这三个）：

| 状态码 | 含义 | 图书馆例子 |
|--------|------|-----------|
| **200** | 成功 | 查到了书 |
| **404** | 找不到 | 查了一本不存在的书 |
| **4xx**（400/401 等） | 客户端你的问题 | 参数漏传了（400）、没登录就想操作（401） |
| **5xx** | 服务器的问题 | 服务器代码崩了（500） |

### JSON：接口世界的普通话

接口返回的数据格式几乎都是 **JSON**——一种"键： 值"写法的文本。对比一下你就懂了：

```
HTML（给人看的页面）：              JSON（给程序用的数据）：
<h3 class="book-title">活着</h3>    {"id": 1, "title": "活着", "status": "可借"}
<p class="status">可借</p>
```

同样一本书，HTML 长得漂亮给人看；JSON 朴素干净给程序读。**接口测试断言的就是 JSON 里的数据**——这比在页面上找元素容易多了。

## 1.4 接口自动化在金字塔里的位置（15 min）

```
        ／ UI 自动化 ＼        ← 秒级、脆、量少 —— 保核心路径
       ／ 接口自动化   ＼       ← 毫秒级、稳、量大 —— 本方案主角，主力军
      ／ 单元自动化     ＼      ← 毫秒级、最稳、最多 —— UT 方案学的
     ‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
```

一条业务规则（比如"借书超上限要拒绝"），**三层都能测**：单元层测 `can_borrow()` 函数、接口层测 `POST /api/borrow`、UI 层测页面提示。**越往下越快越稳，能在下层测的不要推到上层**——接口层就是那个"性价比最高"的中间层：比单元层更接近真实（走完整请求），比 UI 层快十倍且不怕改版。

## 1.6 接口测试用例长什么样（40 min）

用例三要素不变，只是每一要素换了形态：

| 用例要素 | UI 自动化里 | 接口自动化里 |
|---------|------------|-------------|
| 前置条件 | 页面处于某状态 | 数据处于某状态（如"书 2 已借出"） |
| 操作步骤 | 打开页面、点击元素 | **发一个请求**（方法 + 网址 + 参数） |
| 预期结果 | 元素可见、文本正确 | **状态码 + 响应体数据** |

拿"查一本书"接口（假想的 `GET /api/books/<编号>`）设计用例表：

| 编号 | 用例标题 | 请求 | 预期 | 设计方法 |
|------|---------|------|------|---------|
| TC01 | 查存在的书 | GET /api/books/1 | 200；响应里 title=活着 | 正常场景 |
| TC02 | 查不存在的书 | GET /api/books/999 | 404 | 无效等价类 |
| TC03 | 编号传成文字 | GET /api/books/abc | 400 或 404（按文档约定） | 异常输入 |
| TC04 | 不传编号 | GET /api/books/ | 404/405（按文档约定） | 异常输入 |

> 注意 TC03/TC04 的预期"按文档约定"——接口的行为以**接口文档**为准，测试前先拿到文档或问清约定，这叫"以文档为预期依据"。

# Day 2：造靶子 + 第一个接口自动化脚本

> **今天的目标**：先用 Flask 造一个迷你图书馆 API（被测对象），再用 requests + pytest 写出第一批接口自动化用例。

## 2.1 先造被测接口：迷你图书馆 API（50 min）

**前置**：虚拟环境已激活（提示符前有 `(.venv)`）。安装 Flask：

```powershell
pip install flask requests
```

新建 `api/app.py`，完整代码如下（照抄即可，注释解释了每一段在干什么——读这段代码本身就是今天的学习内容）：

```python
# api/app.py
"""迷你图书馆 API —— 我们亲手造的被测对象

只提供 4 个接口，覆盖"查、查一个、借、重置"，麻雀虽小五脏俱全。
数据存在内存里（重启程序就还原），学习阶段够用。
"""
import copy

from flask import Flask, jsonify, request

app = Flask(__name__)
app.json.ensure_ascii = False   # 让中文直接显示，而不是 \uXXXX 转义

# —— 图书数据（初始库存）——
INITIAL_BOOKS = [
    {"id": 1, "title": "活着",   "author": "余华",           "status": "available"},
    {"id": 2, "title": "三体",   "author": "刘慈欣",         "status": "borrowed"},
    {"id": 3, "title": "百年孤独", "author": "加西亚·马尔克斯", "status": "available"},
]
BOOKS = copy.deepcopy(INITIAL_BOOKS)      # 当前库存（会被借书操作改动）
BORROWED_COUNT = {"reader_001": 0}        # 每位读者已借数量
MAX_BORROW = 5                            # 借书上限 —— 和 UT 方案的规则一致！


# 接口1：查全部图书
@app.get("/api/books")
def list_books():
    return jsonify({"code": 0, "data": BOOKS})


# 接口2：查一本图书（编号不存在时返回 404）
@app.get("/api/books/<int:book_id>")
def get_book(book_id):
    for book in BOOKS:
        if book["id"] == book_id:
            return jsonify({"code": 0, "data": book})
    return jsonify({"code": 404, "msg": "图书不存在"}), 404


# 接口3：借书（复用 UT 方案 Day1 的借书规则！）
@app.post("/api/borrow")
def borrow():
    body = request.get_json(silent=True) or {}
    book_id = body.get("book_id")
    reader_id = body.get("reader_id", "reader_001")

    if book_id is None:                                   # 参数缺失
        return jsonify({"code": 400, "msg": "参数错误：缺少 book_id"}), 400
    book = next((b for b in BOOKS if b["id"] == book_id), None)
    if book is None:                                      # 图书不存在
        return jsonify({"code": 404, "msg": "图书不存在"}), 404
    if book["status"] != "available":                     # 已借出
        return jsonify({"code": 400, "msg": "图书已借出"}), 400
    if BORROWED_COUNT.get(reader_id, 0) >= MAX_BORROW:    # 超出上限
        return jsonify({"code": 400, "msg": "超出可借上限"}), 400

    book["status"] = "borrowed"                           # 执行借出
    BORROWED_COUNT[reader_id] = BORROWED_COUNT.get(reader_id, 0) + 1
    return jsonify({"code": 0, "msg": "借出成功"})


# 接口4：重置数据（专供测试用！Day4 会大用它）
@app.post("/api/reset")
def reset():
    global BOOKS
    BOOKS = copy.deepcopy(INITIAL_BOOKS)
    BORROWED_COUNT.clear()
    BORROWED_COUNT.update({"reader_001": 0})
    return jsonify({"code": 0, "msg": "已重置"})


if __name__ == "__main__":
    app.run(port=5000)
```

启动它（新开一个终端，像 UI 方案里的静态服务器一样，它会"卡住"——正常，它在服务）：

```powershell
cd C:\project\book
.venv\Scripts\Activate.ps1
python api/app.py
```

**你会看到**：`Running on http://127.0.0.1:5000`。然后拿浏览器验证（地址栏输入，等于发 GET）：

| 网址 | 你会看到 |
|------|---------|
| `http://localhost:5000/api/books` | 全部图书的 JSON 列表 |
| `http://localhost:5000/api/books/1` | 《活着》一本书的 JSON |
| `http://localhost:5000/api/books/999` | 一段 404 错误信息 JSON（浏览器会显示"Not Found"字样的错误页，看 JSON 内容要点 Postman，见下） |

**对照 Day1 的知识**：三个网址 = 三个请求；返回 = 三个响应；第三个就是一条反向用例的真实表现。

## 2.2 用 Postman 手工调一遍（30 min）

GET 用浏览器就够了，但 POST（借书）浏览器发不了，用 **Postman**（最流行的接口调试图形工具，官网 https://www.postman.com/downloads 下载安装，免费用）：

1. 新建 Request → 方法选 **POST**，网址填 `http://localhost:5000/api/borrow`
2. 选 **Body → raw → JSON**，填入：

```json
{ "book_id": 1, "reader_id": "reader_001" }
```

3. 点 **Send**。**你会看到**：下方返回 `{"code": 0, "msg": "借出成功"}`，状态码 **200 OK**
4. 再 Send 一次（书已经被借走了）。**你会看到**：`{"code": 400, "msg": "图书已借出"}`——**你刚刚亲手触发了一条边界用例**

> 手工调接口的习惯值得保持：**写自动化用例前，先用 Postman 手工把每个接口点一遍**，看清真实的返回长什么样，预期值才不会写错。

## 2.3 requests：用 Python 发请求（30 min）

requests 是 Python 最流行的"发 HTTP 请求"库，把 Postman 里点的那些变成代码。在终端里输入 `python` 进入交互模式，逐行体验：

```python
>>> import requests
>>> r = requests.get("http://localhost:5000/api/books/1")
>>> r.status_code          # 状态码
200
>>> r.json()["data"]["title"]   # 把响应体解析成字典，取书名
'活着'
>>> r2 = requests.get("http://localhost:5000/api/books/999")
>>> r2.status_code
404
```

就四个动作，接口测试的全部原料齐了：**发请求（get/post）、看状态码（status_code）、读数据（json()）**。输入 `exit()` 退出交互模式。

## 2.4 第一条接口自动化用例（40 min）

新建 `api/test_books_api.py`：

```python
# api/test_books_api.py
import requests

BASE = "http://localhost:5000"    # 被测服务地址


def test_list_books_returns_200():
    """查全部图书 → 200，且包含《活着》"""
    resp = requests.get(f"{BASE}/api/books")

    assert resp.status_code == 200                     # 断言① 状态码
    titles = [b["title"] for b in resp.json()["data"]]  # 取出所有书名
    assert "活着" in titles                             # 断言② 关键数据


def test_get_existing_book():
    """查 1 号书 → 200，书名是《活着》"""
    resp = requests.get(f"{BASE}/api/books/1")

    assert resp.status_code == 200
    assert resp.json()["data"]["title"] == "活着"


def test_get_missing_book_returns_404():
    """查 999 号书（不存在）→ 404"""
    resp = requests.get(f"{BASE}/api/books/999")

    assert resp.status_code == 404
    assert resp.json()["msg"] == "图书不存在"
```

运行（**确保 `python api/app.py` 那个终端还开着**；测试命令在项目根目录执行）：

```powershell
pytest api -v
```

**你会看到**：`3 passed`。看懂用例的结构——还是熟悉的三段式：

| UT / UI 里 | 接口里 |
|-----------|--------|
| 构造输入 / 打开页面 | `requests.get(...)` 发请求 |
| 调用函数 / 定位元素 | `resp.status_code`、`resp.json()` 读响应 |
| `assert` 断言 | `assert` 断言（一模一样） |

## 2.5 接口断言三板斧（20 min）

每条接口用例，按这三层检查就基本完整（按需取用）：

| 层 | 检查什么 | 例子 |
|----|---------|------|
| ① 状态码 | 请求办没办成 | `assert resp.status_code == 404` |
| ② 关键字段 | 数据对不对 | `assert resp.json()["data"]["title"] == "活着"` |
| ③ 结构 | 该有的字段都在吗 | `assert "status" in resp.json()["data"]` |

只查状态码不看数据 = 只查了一半（服务器可以 200 但返回空数据）；每条用例至少①+②。

## 3.2 借书接口 = 一张活的判定表（40 min，今天的高光时刻）

## 3.3 同一条规则，三层测试（30 min，建立全局观）

# Day 4：数据管理、鉴权与业务流

> **今天的目标**：解决接口测试特有的两大问题——"用例改坏数据"和"接口要登录才能调"，并把用例串成真实业务流。

## 4.1 数据污染的解法：每条用例后重置数据（50 min，今天最重要）

Day3 留下的问题：借书用例把"1 号书"改成已借出，污染了后续用例的世界。解法分两半：

**服务端**：我们在 Day2 已经埋好了 `POST /api/reset`（把库存恢复初始值）——真实项目里没有现成的重置接口，常见做法是用测试专用数据库/每次造数后清理，思想相同：**测试要能"擦干净桌子"**。

**测试端**：用 pytest 的 `autouse` 夹具，让"重置"对每条用例**自动生效**。新建 `api/conftest.py`（conftest.py 是 pytest 的约定文件，里面的夹具自动对所有用例生效）：

```python
# api/conftest.py
import pytest
import requests

BASE = "http://localhost:5000"


@pytest.fixture(autouse=True)
def clean_data():
    """每条用例结束后，把图书馆数据恢复原状"""
    yield                              # yield 前：用例执行前的准备（暂不需要）
    requests.post(f"{BASE}/api/reset")  # yield 后：用例执行完 → 重置
```

现在再跑 `pytest api`——每条用例都从"干净的图书馆"出发，**单跑绿、合跑也绿**。回头看 3.2 留的"规则2 超上限"，现在能写了：

```python
def test_borrow_over_limit_rejected():
    """规则2：借满 5 本后再借 → 超出可借上限"""
    # 准备：把 1、3 号书都借走（reader_001 已借 2 本，离上限还差 3 本——
    # 本项目初始可借书少，这里验证"规则触发路径"即可，完整上限用例留给重置数据后自造）
    for book_id in (1, 3):
        requests.post(f"{BASE}/api/borrow", json={"book_id": book_id})

    # 没有更多可借的书了：再借任何一本都应被拒绝
    resp = requests.post(f"{BASE}/api/borrow", json={"book_id": 1})
    assert resp.status_code == 400
    assert "借出" in resp.json()["msg"]
```

> 数据准备（开头的 for 循环借书）就是接口测试的"前置条件"落地方式：**用接口本身来造数据**。

## 4.2 带鉴权的接口怎么测（50 min）

真实系统里很多接口要"登录后才能调"。原理很简单：登录后服务器发你一个**令牌（token）**，之后每次请求把它放在**请求头（header）**里带上，服务器验头。我们在 `app.py` 里加一个管理员接口来模拟（追加到 `reset` 接口后面）：

```python
# —— 追加到 api/app.py ——

API_TOKEN = "secret-token-123"   # 假装这是登录后发的令牌


# 接口5：管理员新增图书（需要带 X-Token 请求头）
@app.post("/api/admin/books")
def add_book():
    if request.headers.get("X-Token") != API_TOKEN:
        return jsonify({"code": 401, "msg": "未授权：请先登录"}), 401

    body = request.get_json(silent=True) or {}
    title = body.get("title")
    if not title:
        return jsonify({"code": 400, "msg": "书名不能为空"}), 400

    new_id = max(b["id"] for b in BOOKS) + 1
    book = {"id": new_id, "title": title,
            "author": body.get("author", ""), "status": "available"}
    BOOKS.append(book)
    return jsonify({"code": 0, "data": book}), 201
```

重启服务（`app.py` 终端 Ctrl+C 后重新 `python api/app.py`——改了代码要重启），然后写用例。**鉴权接口必测的一正一反**：

```python
# api/test_admin_api.py
import requests

BASE = "http://localhost:5000"
HEADERS = {"X-Token": "secret-token-123"}


def test_add_book_without_token_401():
    """不带令牌 → 401 未授权（反向）"""
    resp = requests.post(f"{BASE}/api/admin/books", json={"title": "雪国"})
    assert resp.status_code == 401


def test_add_book_with_token():
    """带令牌 + 合法书名 → 201，返回新书"""
    resp = requests.post(
        f"{BASE}/api/admin/books",
        json={"title": "雪国", "author": "川端康成"},
        headers=HEADERS,                      # 请求头：把令牌带上去
    )
    assert resp.status_code == 201
    assert resp.json()["data"]["title"] == "雪国"


def test_add_book_with_empty_title_400():
    """带令牌但书名为空 → 400（参数反向）"""
    resp = requests.post(f"{BASE}/api/admin/books",
                         json={"title": ""}, headers=HEADERS)
    assert resp.status_code == 400
```

不用重置数据吗？不用——新增图书是"加数据"，不影响已有用例的"查/借初始库存"（id 会变大但不冲突）。**要判断哪些用例会污染数据，就重置哪些；判断依据还是"前置条件"**。

## 4.3 业务流用例：接口串起来测（30 min）

场景法在接口层的落地：**上一个接口的输出，是下一个接口的输入**。最真实的例子——借完书，查它，状态应该变了：

```python
def test_borrow_then_check_status():
    """业务流：借书 → 查详情，状态变为 borrowed"""
    borrow_resp = requests.post(f"{BASE}/api/borrow", json={"book_id": 1})
    assert borrow_resp.status_code == 200

    detail_resp = requests.get(f"{BASE}/api/books/1")
    assert detail_resp.json()["data"]["status"] == "borrowed"
```

**什么时候允许链式、什么时候必须独立？**

- ✅ 链式：用例本身测的就是"这条业务流"（如上）
- ❌ 链式：只是为了"图省事"复用上一步——每条用例仍应自己准备数据（用接口造数），互不依赖

> **今天的目标**：把接口测试变成"一条命令全跑 + 每次提交自动跑"。CI 的完整原理在 UI 方案 Day5.3 已讲透（什么是流水线、GitHub Actions、Runner），今天直接复用那套知识——你会发现挂法一模一样。

## 5.1 让 pytest 自动起服务（40 min）

和 UI 方案同款配方：conftest 加一个 session 级夹具，自动启动/关闭 Flask 服务。在 `api/conftest.py` 里**追加**：

```python
import subprocess
import sys
import time
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent.parent   # api/ 的上一级 = 项目根目录


@pytest.fixture(scope="session", autouse=True)
def api_server():
    """整场测试开始前自动启动迷你图书馆服务，结束后自动关闭"""
    proc = subprocess.Popen(
        [sys.executable, str(PROJECT_ROOT / "api" / "app.py")],  # sys.executable = 当前虚拟环境的 python
        cwd=str(PROJECT_ROOT),
    )
    for _ in range(30):                       # 最多等 15 秒直到服务就绪
        try:
            requests.get(f"{BASE}/api/books")
            break
        except Exception:
            time.sleep(0.5)
    yield
    proc.terminate()
```

从此一条命令全包（起服务 → 全部接口测试 → 关服务 → 每条用例自动重置数据）：

```powershell
pytest api
```

> 小坑：如果手动开着 `python api/app.py` 的终端，先 Ctrl+C 关掉再跑，否则端口冲突（报 `Address already in use`）——服务现在由 pytest 全托管了。

## 5.3 挂上 CI 流水线（40 min）

还记得 UI 方案 Day5 的结论吗：**脚本必须挂在自动执行的流水线上才算数**。接口测试的挂法完全一样——新建 `.github/workflows/api-tests.yml`：

```yaml
name: api-tests
on: [push]                    # 每次 push 自动触发
jobs:
  test:
    runs-on: ubuntu-latest    # GitHub 免费提供的云端电脑
    steps:
      - uses: actions/checkout@v4            # 拉代码
      - uses: actions/setup-python@v5        # 装 Python

          python-version: "3.12"
      - run: pip install -r requirements.txt # 装依赖（flask/requests/pytest 都在里面）
      - run: pytest api                      # 跑测试 —— 和本地命令一模一样！
```

`requirements.txt` 确认包含（UT/UI 方案的依赖 + 本方案新增）：

```
pytest-html
requests
flask
```

push 到 GitHub → 仓库的 **Actions** 页 → 看着流水线从黄点变绿勾。云端那个"全新的干净电脑"上，conftest 夹具自动起了 Flask 服务、每条用例自动重置数据——**本地能跑的，CI 就能跑**，这就是前四天把环境管理做规范的全部回报。

## 附录 A：术语速查表

| 术语 | 含义 |
|------|------|
| API / 接口 | 程序之间传数据、传指令的通道（传话的服务员） |
| HTTP 请求/响应 | 一次调用的一来一回 |
| GET / POST | 查数据 / 提交数据（最常用的两个方法） |
| 状态码 | 响应的一句话结论：2xx 成功、4xx 客户端的错、5xx 服务器的错 |
| JSON | 接口返回数据的标准格式，"键： 值"写法 |
| 请求头（Header） | 请求的"附加信息"，放令牌（鉴权）就在这里 |
| Token（令牌） | 登录后发的"通行证"，之后每次请求带上 |
| Postman | 手工调接口的图形化工具 |
| requests | Python 发 HTTP 请求最常用的库 |
| Flask | Python 的迷你 Web 框架，本方案用它造被测接口 |
| 数据污染 | 用例改动了数据，影响其他用例甚至下次执行 |
| 重置 / 造数 | 恢复初始数据 / 用接口准备前置数据 |
| Schema 校验 | 用一份"结构说明书"检查响应字段齐不齐、类型对不对 |
| 回归 / CI / 流水线 | 见前两份方案附录（含义完全通用） |

## 附录 B：常见问题

**Q：`requests.exceptions.ConnectionError`？**
服务没起来。Day5 前手动开 `python api/app.py`（别关）；Day5 后确认没有把 conftest 里的夹具删掉。

**Q：`Address already in use` / 端口被占用？**
5000 端口已有服务。关掉旧的那个 `python api/app.py` 终端；实在关不掉就换端口（`app.run(port=5001)`，同时改测试里的 `BASE`）。

**Q：返回的中文变成 `\u6d3b\u7740` 这种乱码？**
程序没坏——那是 Unicode 转义，`resp.json()` 解析后就是正常中文。想让浏览器直接显示中文，确认 `app.py` 里有 `app.json.ensure_ascii = False`。

**Q：单跑绿、合跑红？**
Day4 的主题：数据污染。检查 `conftest.py` 的 `clean_data` 夹具是否在位。

**Q：PowerShell 里 `curl` 命令的行为和教程不一样？**
PowerShell 的 `curl` 是 `Invoke-WebRequest` 的别名，不是真 curl。初学阶段直接用浏览器（GET）和 Postman（POST/带请求头），不折腾命令行。

**Q：真实项目里怎么知道有哪些接口、参数是什么？**
看接口文档（问开发要，或找 Swagger/OpenAPI 页面）。没有文档时，用 Postman + 抓浏览器 F12 的 Network 面板逆向——那是进阶课了。
