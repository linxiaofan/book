# 自动化测试初学者 5 天学习方案（Python · 小白友好版）

> **面向对象**：零基础的测试/开发初学者。不懂 Git 分支、不懂命令行也没关系，每一步都写清楚"输入什么、会看到什么"。
> **建议投入**：每天 2~4 小时。
> **技术栈**：Python + **pytest-playwright**（不用怕这两个名词，Day2 会从安装开始手把手带你）。

## 开始之前：这份方案在教你什么（先读这段）

用一句话概括：**你要学的，是把"人工在浏览器里点点点检查页面"这件事，变成"机器人自动检查，还能每天自动执行"。**

举个例子：本项目（书香阁图书馆网站）是多人协作的，大家经常改页面。每次改完，都得有人把 3 个页面挨个点一遍，确认没改坏——很枯燥，还容易漏。学完这 5 天，你只需要敲一条命令 `pytest e2e`，十几秒后电脑自动告诉你："3 个页面、8 本书、所有跳转，全部正常 ✓"或者"第 5 项检查失败 ✗，问题出在这里"。

大公司的网站每次更新都要跑成百上千条这样的自动检查，不然根本不敢发布。你学的就是这套东西的最小版本。

**怎么用这份方案：**

1. **每天一个 Day，按顺序学**。Day1 照例"自顶向下"：先带你看清全貌——自动化测试是什么、业内成熟的开源项目长什么样——然后再动手。
2. 本项目是**纯静态网站（3 个页面、8 本书卡片、没有后端）**，Playwright 直接就能测，不需要搭任何服务器环境，非常适合入门。
3. 每天末尾有 **作业** 和 **检验清单**，全部达成再进入下一天。
4. 命令为 **Windows PowerShell** 写法；本项目所有测试命令都**在项目根目录**执行（单元测试 `pytest ut`，自动化测试 `pytest e2e`——带目录参数才能读到各自的配置）。

## 学完你能做到什么

- 理解 **CI 流水线**是什么，并把自己的测试脚本挂上去：一 push 代码，云端自动跑测试

# Day 1：自顶向下 —— 自动化测试全景

> **今天的目标**：不写代码。搞懂三件事——自动化测试是什么、业内的成熟项目长什么样、自动化用例和手工用例的区别。
> **与 UT 方案的关系**：测试用例的三要素（前置条件/操作步骤/预期结果）完全通用，今天只学"自动化对用例提出的两个新要求"。

## 1.1 手工测试 vs 自动化测试（30 min）

想象这个真实场景：本项目是多人 Git 协作，大家都在改 `css/style.css`，每次合并冲突解决完，你都要**人肉把 3 个页面各点一遍**确认没改坏。一天合并 5 次，一周下来就是几十次重复点击——而且人肉检查总会漏。

自动化测试 = **把这套重复的"点一遍"写成脚本，让机器执行**：

| | 手工测试 | 自动化测试 |
|--|---------|-----------|
| 一次投入 | 低 | 高（要先写脚本） |
| 重复执行成本 | 高，而且人会疲劳、会漏检 | 几秒~几分钟，结果永远稳定 |
| 适合 | 探索性测试、一次性验证、"好不好看" | **反复执行的回归测试** |
| 发现新 bug 的能力 | 强（人会好奇地乱点） | 弱（只检查脚本写到的点） |

一个新手必背的词：

> **回归（Regression）**：以前好的功能，被后来的改动弄坏了。
> **回归测试**：防止这种事发生的测试。**自动化测试的主战场就是回归测试。**

### 什么值得自动化，什么不值得

| 值得自动化 ✓ | 不值得自动化 ✗ |
|-------------|---------------|
| 高频回归的核心路径（本项目：页面渲染、导航跳转） | 只跑一次的验证 |
| 每次发版前必查的清单 | 探索性测试（找新 bug 靠人） |
| 明确可判定的检查（文本、数量、状态、网址） | 主观视觉感受（"好不好看"，机器判断不了） |
| 数据驱动的批量检查（8 本书逐个验证） | 快速废弃中的功能 |

## 1.2 自动化测试分层（30 min）

"自动化"不只有"点网页"一种。测试金字塔的三层，各自都可以自动化：

```
        ／ UI 自动化 ＼        ← 模拟用户操作真实页面（本方案主角）
       ／ 接口自动化   ＼       ← 不打开页面，直接调 HTTP 接口验证（本项目暂无后端，先了解）
      ／ 单元自动化     ＼      ← UT 方案 5 天学的内容
     ‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
```

| 层 | 对象 | 速度 | 稳定性 | 数量建议 |
|----|------|------|--------|---------|
| 单元自动化 | 函数逻辑 | 毫秒 | 最稳 | 最多 |
| 接口自动化 | HTTP API | 快 | 稳 | 中等 |
| UI 自动化 | 真实页面 | 慢（秒级） | 相对脆（页面常变） | **少而精：核心路径** |

注意 UI 层在塔尖、数量最少——它最接近真实用户，但最慢最脆，**只把核心路径放上来**。本项目没有后端，所以我们练的就是 UI 层；将来项目加了接口，再用 Python 的 `requests` 库补接口自动化。

## 1.3 参观成熟项目：专业的自动化在 GitHub 上长什么样（40 min，今天特色环节）

自顶向下学的好处就是：**先看看行业里做得很成熟的项目长什么样，再自己动手**。下面 4 个开源项目都在 GitHub 上，是全球使用最广的自动化测试项目。你不需要看懂里面的代码，只要带着 3 个问题去"参观"：

> **参观时要找的三样东西：**
> ① `tests/`（或 `testing/`）目录——自动测试脚本都住在这里
> ② `.github/workflows/` 目录——CI 流水线的配置文件（Day5 你会亲手写一个）
> ③ README 顶部的**小徽章（badge）**——比如一个写着 "build passing" 的绿色小图标，意思是"每次提交代码，云端都自动跑了测试，目前是绿的"

| 项目 | 地址 | 是什么 | 参观看点 |
|------|------|--------|---------|
| **Playwright** | https://github.com/microsoft/playwright | 微软的 UI 自动化框架，**我们这套方案用的就是它** | 看它 README 顶部的徽章；进 `tests/` 目录——它用自己测自己，里面全是端到端测试 |
| **Selenium** | https://github.com/SeleniumHQ/selenium | 自动化测试的祖师爷（2004 年至今），行业标准 | 看它的测试目录结构；感受"20 年的老项目长什么样" |
| **Cypress** | https://github.com/cypress-io/cypress | 另一个流行的 UI 自动化框架（JS 系） | 对比 README 的写法：好项目的 README 会教你 5 分钟跑起来 |
| **Appium** | https://github.com/appium/appium | 手机 App 的自动化（扩展视野） | 体会"UI 自动化"不只网页，还有 App |

**参观结论（记住这个，比记住任何工具都重要）**：一个成熟的自动化工程 = **测试脚本（tests/）+ CI 流水线配置（.github/workflows/）+ 状态徽章**。脚本只是三分之一——**脚本必须挂在自动执行的流水线上，才能真正保护项目**。这正是你 5 天后的成品结构，Day5 我们会亲手把脚本挂上 CI。

## 1.4 从手工用例到自动化用例（60 min，今天最重要的技能）

回顾一下，一条测试用例 = **前置条件 + 操作步骤 + 预期结果**（UT 方案 Day1 学的三要素）。写自动化用例时三要素不变，但每一步要多满足两个要求：

1. **可定位**：步骤里操作/检查的每个元素，脚本都得"找得到"（靠什么找？稳定的文本、class、角色……）
2. **可断言**：预期结果必须是程序能验证的（具体的文本、数量、状态、网址）

### 改写示范

**例 1：** 手工用例"打开首页，看看书展示得正不正常"

| | 改写后 |
|--|--------|
| 步骤 | 打开首页 `index.html` |
| 预期 | 页面标题包含"书香阁图书馆"；存在 8 张书籍卡片（`.book-card`）；每张卡片内有书名（`.book-title`）和状态标签（`.status`） |

> "看看正不正常"机器没法判定；改写后每一项都是机器能验证的。

**例 2：** 手工用例"点'图书馆介绍'链接，确认跳转成功"

| | 改写后 |
|--|--------|
| 前置 | 已打开首页 |
| 步骤 | 点击导航栏文本为"图书馆介绍"的链接 |
| 预期 | 当前网址变成 `about.html`；页面出现 `<h1>` 大标题 |

### 改写心法（写每条用例前自问两句）

- 这一步问自己：**脚本靠什么找到这个元素？**（文本？class？角色？）
- 预期问自己：**程序怎么知道它对了？**（比网址？数数量？比文本？）
- 答不上来的，用浏览器按 F12 打开开发者工具，右键元素 → "检查"，看它的 HTML 长什么样，找到稳定特征再落笔

## 1.5 工具怎么选（15 min）

| 工具 | 特点 | 一句话点评 |
|------|------|-----------|
| Selenium | 老牌、W3C 标准、支持语言最多 | 生态最大，但要自己装浏览器驱动、手写等待 |
| **Playwright** | 微软出品，自动等待、自带录制器和失败回放，官方支持 Python | **本方案选择：对初学者最友好** |
| Cypress | 开发体验好 | 只支持 JS/TS，限制较多 |

Playwright 三个杀手锏，后面天天用：`codegen`（你点鼠标，它帮你写代码）、自动等待（不用手写 sleep）、`trace`（失败后一步步回放你当时干了什么）。

# Day 2：第一个自动化脚本（pytest + Playwright）

> **今天的目标**：环境跑通，写出第一批脚本，亲眼看浏览器自己动起来。

## 2.1 环境准备（40 min）

前提：UT 方案的 Python 虚拟环境已就绪（`.venv` 已激活，终端提示符前面有 `(.venv)` 字样）。没做过的先回 UT 方案 2.1 补上，10 分钟的事。

然后装两样东西（**在项目根目录、已激活虚拟环境的终端里**执行）：

```powershell
pip install pytest-playwright     # ① Playwright 库 + pytest 插件
playwright install chromium       # ② 下载一个专用 chromium 浏览器（100+ MB，耐心等进度条）
```

> 第一条装的是 Python 库（让 pytest 能指挥浏览器）；第二条下载的是它专用的浏览器（就像给机器人配了一双眼睛）。下载的浏览器放在用户目录，不污染你的日常 Chrome。

装完验证一下：

```powershell
pytest --version                  # 能显示版本号即成功
```

最后在项目根目录新建一个文件夹 `e2e/`——以后所有自动化脚本都住这里（e2e 读作"一图图"，End-to-End 的缩写，意思是"端到端"，模拟用户从头到尾的使用）。

## 2.2 让网站"跑"在本地服务上（20 min）

自动化脚本需要通过网址（http:// 开头）访问页面，所以要先把本项目变成一个"本地小网站"。Python 自带这个能力，**零安装**，开一个**新终端**（原来的终端别关）：

```powershell
cd C:\project\book
python -m http.server 3000
```

> 这行命令的意思：把当前文件夹变成一个网站服务器，端口号 3000。终端会显示 `Serving HTTP ... port 3000`，然后**看起来卡住不动——这是正常的**，它正在服务，别关。

验证：打开日常浏览器，访问 `http://localhost:3000/index.html`，能看到图书馆首页就成功了。

> 为什么不直接双击 HTML 文件打开（file:// 开头）？本项目恰好可以，但真实项目里 file:// 会导致路径、跨域等各种问题——从第一天就养成"本地服务"的正确习惯。

## 2.3 项目配置（30 min）

测试有一些"固定设置"（比如网址前缀、失败时自动截图），写在一个配置文件里，免得每次敲命令都重复。新建 `e2e/pytest.ini`（pytest.ini 是 pytest 的配置文件，ini 就是一种"键 = 值"的简单配置格式）：

```ini
[pytest]
# 每次执行 pytest e2e 时，自动附加这些参数
addopts =
    --base-url=http://localhost:3000
    --screenshot=only-on-failure
    --tracing=retain-on-failure
markers =
    smoke: 冒烟用例，每次必跑
```

用人话解释每一行：

- `--base-url=...`：以后脚本里写 `page.goto("/index.html")` 就够了，不用每次写完整网址
- `--screenshot=only-on-failure`：哪条检查失败了，自动给它拍一张"遗照"，方便你看当时页面长什么样（Day3 细讲）
- `--tracing=retain-on-failure`：失败了自动保存"行车记录仪"录像，可以一步步回放（Day3 细讲）
- `markers`：注册一个名叫 smoke 的标签，给最重要的用例用（Day4 用到）

> **运行方式约定（重要）**：始终在项目根目录执行 `pytest e2e`——带上 `e2e` 这个目录参数，pytest 才会读到这份配置。

顺手更新 `.gitignore`，加两行（自动化产物不该进 git）：

```
test-results/
report.html
```

## 2.4 写第一条脚本（60 min）

新建 `e2e/test_home.py`，把下面的代码抄进去（放心抄，每行都有注释）：

```python
# e2e/test_home.py
from playwright.sync_api import expect, Page


def test_home_shows_huozhe_available(page: Page):
    """首页展示《活着》且状态为可借"""
    page.goto("/index.html")                                # ① 打开首页

    card = page.locator(".book-card", has_text="活着")       # ② 定位：找含"活着"的书籍卡片
    expect(card).to_be_visible()                            # ③ 检查：卡片看得见
    expect(card.locator(".status")).to_have_text("可借")      # ④ 检查：它的状态文字是"可借"
```

运行（回到项目根目录的终端；那个跑着 `http.server` 的终端是另一个，别动它）：

```powershell
pytest e2e -v               # 无头模式：浏览器在后台跑，看不见但最快
pytest e2e --headed         # 有头模式：弹出一个真浏览器窗口，亲眼看它自己操作（学习期推荐！）
```

**你会看到**：弹出一个浏览器窗口，自动打开首页，闪一下就关了；终端输出 `1 passed`——恭喜，你的第一条自动化用例通过了。

看懂这条脚本的三个角色（后面天天见）：

- `page`：代表一个浏览器标签页。它不需要你创建——写进函数参数 `page: Page`，pytest 会自动准备好递给你（这种机制叫**夹具 fixture**，UT 方案 Day3 见过 monkeypatch，同一个思想）
- `locator(...)`：**定位器**——"某个元素怎么找"的说明书。注意：声明它的时候还没真的去找，到检查那一步才找
- `expect(...)`：检查（断言），和 UT 里的 `assert` 一个思想，但多了"自动等待"超能力（Day3 细讲）

对照 Day1.4 的改写表：`goto` 是步骤，`to_be_visible`/`to_have_text` 就是那条"可断言"的预期——**你已经在执行自己 Day1 写的用例表了**。

## 2.5 定位器入门（40 min）

定位器决定脚本"找不找得到、找得稳不稳"。像在人群中找朋友：按身份证号找（唯一但难记）？按长相找（会认错人）？按"穿红色衣服的那位"找（简单稳定）？定位元素同理，常用四招，优先级从高到低：

| 方式 | 写法 | 适用 |
|------|------|------|
| **按角色**（最推荐） | `page.get_by_role("link", name="图书馆介绍")` | 有语义的元素：链接、按钮、标题 |
| **按文本** | `page.get_by_text("开放时间")` | 靠内容识别的元素 |
| **按 CSS class** | `page.locator(".book-card")` | 有稳定 class 的元素（本项目大量使用） |
| **按层级组合** | `card.locator(".status")` | 先找到某本书的卡片，再在卡片里面找状态标签 |

本项目页面的定位速查表（都来自真实 HTML，可直接用）：

| 想找什么 | 定位器 |
|------|--------|
| 某本书的卡片 | `page.locator(".book-card", has_text="活着")` |
| 卡片里的书名 | `card.locator(".book-title")` |
| 卡片里的状态标签 | `card.locator(".status")` |
| 所有"已借出"的书 | `page.locator(".status.borrowed")` |
| 导航链接 | `page.get_by_role("link", name="管理员介绍")` |
| 页脚 | `page.locator(".site-footer")` |

> 这些 class 名哪来的？浏览器按 F12 → 点左上角小箭头图标 → 再点页面上的元素，右侧就是它的 HTML，`.book-card` 就是 `class="book-card"` 的意思（`.` 表示 class）。

# Day 3：稳定与调试 —— 等待、检查、失败分析

> **今天的目标**：解决 UI 自动化最大的痛点——"脚本时好时坏"，并学会失败后快速定位原因。UI 自动化一定会失败，**失败不丢人，快速定位才是本事**。

## 3.1 自动等待：为什么永远不要写死"等 3 秒"（40 min）

页面加载需要时间，元素不是瞬间出现的。新手常写出这种"碰运气"的代码：

```python
# ❌ 坏写法：死等 3 秒再检查。
# 网速快时白白浪费 3 秒；网速慢时 3 秒不够，照样失败 —— 全凭运气
page.wait_for_timeout(3000)
expect(card).to_be_visible()
```

Playwright 的 `expect` 自带**自动等待**：它会在超时时间内**一遍遍重试**，元素一出现立刻通过，元素一直不出现才报失败：

```python
# ✓ 好写法：自动等待（默认最长 5 秒）
# 网速快就快点过，网速慢就多等等 —— 永远"等到能判断为止"，不猜
expect(card).to_be_visible()
```

> **铁律：等待交给 expect，代码里禁止出现 `wait_for_timeout`。** 写死等待几乎都是在掩盖真正的定位或检查问题。

## 3.2 常用检查（断言）清单（40 min）

| 断言 | 人话 | 本项目例子 |
|------|------|-----------|
| `to_be_visible()` / `to_be_hidden()` | 看得见 / 看不见 | 状态标签可见 |
| `to_have_text("可借")` | 文字**完全等于** | 卡片状态文字 |
| `to_contain_text("书香路")` | 文字**包含** | 页脚地址 |
| `to_have_count(8)` | 数量正好是 N | 8 张书籍卡片 |
| `to_have_url(re.compile(r"about\.html$"))` | 当前网址匹配 | 跳转后网址 |
| `to_have_title(re.compile("书香阁"))` | 页面标题匹配 | 各页标题 |

（`re.compile` 是 Python 的正则表达式，先照抄会用即可，"匹配包含某段文字的网址"之意。）

写死这些预期值之前，先到真实页面上数一数、看一看——**如果脚本里的预期值本身写错了，脚本会"忠实地"验证一个错误**。

## 3.3 失败调试三件套：截图、trace、报告（50 min）

UI 自动化失败后，怎么知道"当时发生了什么"？Playwright 给了三个黑匣子，都已在 Day2 的配置里自动开启：

1. **失败截图**（`--screenshot=only-on-failure`）：失败那一刻的页面照片。存在 `test-results/` 文件夹里对应用例的子目录中，直接双击打开看
2. **trace 回放**（`--tracing=retain-on-failure`）：完整的"行车记录仪"，能逐帧回放每一步操作、当时的页面长什么样、发了什么网络请求：

```powershell
playwright show-trace test-results/对应目录/trace.zip    # 路径在测试失败输出里能找到
```

   打开后像看录像一样，点任何一步都能看到当时的页面快照——**哪一步开始不对劲，一目了然**
3. **HTML 报告**（可选，装个小插件，把所有结果汇总成一页网页）：

```powershell
pip install pytest-html
pytest e2e --html=report.html --self-contained-html   # 生成 report.html，浏览器打开
```

### 实战演练（15 min，必做）

故意把定位器写错（把 `".book-card"` 写成 `".book-cardx"`），跑 `pytest e2e` → 变红 → 打开失败截图和 trace，读错误信息 `Timeout ... waiting for locator(".book-cardx")`（意思是"找了半天找不到 .book-cardx 这个元素"）→ 改回来 → 变绿。**这套"失败 → 看黑匣子 → 定位 → 修复"的流程就是 UI 自动化的日常工作，今天必须完整走一遍。**

## 3.4 用例独立性（30 min）

UT 方案的 FIRST 原则里，**I（Independent 独立）**在 UI 自动化里最重要：

- 每条用例**自己打开需要的页面**（开头都有 `page.goto(...)`），不依赖"上一条用例刚好停在哪个页面"
- 任何一条**单独跑、乱序跑**都必须通过

好消息：**pytest-playwright 默认给每条用例分配一个全新的浏览器上下文**（相当于每条用例都拿到一个崭新的浏览器），互相不会影响。你要做的就是把 `goto` 写在每条用例开头：

```python

def test_home_has_2_borrowed_books(page: Page):
    """首页有 2 本书处于已借出状态"""
    page.goto("/index.html")
    expect(page.locator(".status.borrowed")).to_have_count(2)
```

验证独立性的方法：单跑一条试试——

```powershell

```

## 4.1 有效检查 vs 无效检查（40 min）

UT Day4 的教训在 UI 层照样成立：**没有断言的脚本不是测试，只是演示**。

```python
# ❌ 跑完什么也没检查 —— 打开页面就算过，哪怕页面白屏也是"过"
def test_demo_only(page: Page):
    page.goto("/index.html")
```

写检查时按四个维度配齐，用例就立体了：

| 维度 | 验证什么 | 本项目示例 |
|------|---------|-----------|
| 结构 | 元素存在/可见 | 卡片 `.book-card` 可见 |
| 内容 | 文字正确 | 状态标签 `to_have_text("可借")` |

| 数量 | 个数正确 | `to_have_count(8)` |

再对照 Day1 的用例表逐条核对：**用例表里的每条预期，都要在脚本里找到对应的检查**；找不到的，要么补检查，要么说明这条预期本来就该改写。

## 4.2 用类组织 + 标签分层（30 min）

用例多了要分类收纳。pytest 的方式：按文件分模块（一个功能一个文件）+ 类分组：

```python

from playwright.sync_api import expect, Page


class TestHomeBooks:
    """首页书籍展示"""

    def test_8_cards(self, page: Page):
        page.goto("/index.html")
        expect(page.locator(".book-card")).to_have_count(8)

    def test_each_card_has_title_and_status(self, page: Page):
        page.goto("/index.html")
        first_card = page.locator(".book-card").first
        expect(first_card.locator(".book-title")).not_to_be_empty()
        expect(first_card.locator(".status")).to_be_visible()


class TestNavigation:
    """导航跳转"""

    def test_nav_to_about(self, page: Page):
        page.goto("/index.html")
        page.get_by_role("link", name="图书馆介绍").click()
        expect(page).to_have_url(re.compile(r"about\.html$"))
```

再给"每次必跑"的 P0 用例打上标签（markers 已在 pytest.ini 注册过）：

```python

def test_home_shows_huozhe_available(page: Page):
    ...
```

```powershell
pytest e2e -m smoke        # 只跑打了 @smoke 标签的冒烟用例
```

> "冒烟测试"这个词来自硬件行业：新电路板通电，先看冒不冒烟——冒烟了就不用测别的了。软件里指"最基本的检查先过一遍，确认系统没崩"。

组织原则：**按业务功能分组**（不是按页面文件），报告里会按类分块展示；P0/P1/P2 的取舍依据就是 Day1.6 那张检查点清单。

## 5.3 什么是 CI 流水线（60 min，今天最重要的内容）

### 5.3.1 先说痛点

现在的问题：测试脚本在你电脑上，跑不跑全看你自觉。真实的团队里：

- 队友 A push 了一段代码，忘了跑测试，把页面改坏了
- 三天后队友 B 才发现，此时已经分不清是谁、哪次提交改坏的
- 大家互相指责，需求延期

解决思路：**能不能不靠人的自觉，让"跑测试"这件事自动发生？** ——每次有人 push 代码，服务器自动把最新代码拉下来、自动跑一遍全部测试、把结果告诉所有人。这就是 **CI**。

### 5.3.2 CI 是什么

> **CI = Continuous Integration，持续集成**：团队成员频繁地（通常每天多次）把代码合入主干；**每次合入，都自动执行一遍"拉代码 → 装环境 → 跑测试 → 报告红绿"**，用机器的纪律代替人的自觉。

而这条**自动执行、按顺序衔接的步骤链**，就叫**流水线（Pipeline）**——名字来自工厂流水线：原料（代码）从一头进去，经过一道道工序（拉取、安装、测试），末尾自动产出成品（红/绿结论）。流水线上的每道工序叫一个**阶段（Stage）或步骤（Step）**。

```
 开发者执行 git push
        │
        ▼
 ┌─────────── GitHub 的云端电脑（Runner）───────────┐
 │                                                  │
 │  步骤① checkout：拉取最新代码                      │
 │  步骤② 安装 Python 和项目依赖（pip install ...）    │
 │  步骤③ 安装浏览器（playwright install chromium）   │
 │  步骤④ 跑测试（pytest e2e）                       │
 │  步骤⑤ 出结论：全绿 ✓ / 有红 ✗                     │
 │        ↓                  ↓                      │
 │   给这次提交打上           邮件/页面通知提交者，     │
 │   绿色/红色标记            这次提交被打上红叉        │
 └──────────────────────────────────────────────────┘
```

> **Runner（运行器）**：执行流水线的机器。你不用买服务器——GitHub 免费提供云端虚拟机，每次流水线启动时临时开一台全新的电脑，跑完自动销毁。**"每次都是一台全新的、干净电脑"**这一点很重要：它能逼出"我电脑上能跑、别人电脑跑不起来"的问题。

### 5.3.3 GitHub Actions：把流水线写成一个文件

**GitHub Actions** 是 GitHub 内置的 CI 服务（类似的还有 GitLab CI、Jenkins、Gitee Go，思想完全一样）。它的用法简单得出奇：

> **在项目的 `.github/workflows/` 目录里放一个 YAML 文件**，里面用文字描述"什么时候触发、执行哪几步"。GitHub 检测到这个文件，就会照着执行。

YAML 是一种用缩进表示层级的配置文件格式（Day2 的 pytest.ini 是"键=值"，YAML 是它的进阶版，像写大纲一样写配置）。

还记得 Day1 参观 Playwright 仓库时看到的 `.github/workflows/` 目录吗？——他们家的 CI 就是这么配置的。现在轮到你自己写了。

### 5.3.4 亲手把脚本挂上去（每行都有解释）

新建文件 `.github/workflows/e2e.yml`：

```yaml
name: e2e-tests              # ⓪ 流水线的名字（页面上显示用）

on: [push]                   # ① 触发条件：每次有人 push 代码就运行

jobs:                        # ② 一个流水线由若干"任务(job)"组成
  test:                      # ③ 我们只有一个任务，取名 test
    runs-on: ubuntu-latest   # ④ 在 GitHub 提供的 Ubuntu 云端电脑上执行
    steps:                   # ⑤ 这个任务按顺序执行以下步骤
      - uses: actions/checkout@v4          # 步骤1：拉取最新代码（checkout 是官方现成的动作）
      - uses: actions/setup-python@v5      # 步骤2：装好 Python
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt      # 步骤3：装项目依赖（就是你的 requirements.txt）
      - run: playwright install --with-deps chromium   # 步骤4：装 chromium 浏览器
      - run: pytest e2e                           # 步骤5：跑测试！和你本地敲的命令一模一样
```

把项目 push 到 GitHub（本项目本来就有远程仓库），然后打开 GitHub 仓库页面 → 顶部 **Actions** 标签页——**你会看到**：一条流水线正在转黄点（执行中），几分钟后变绿勾 ✓。点进去能看到每一步的详细日志，`pytest e2e` 那一步会打印出和你本地一样的测试结果。

注意一个漂亮的巧合：**云端第 5 步执行的 `pytest e2e`，和你本地敲的命令一模一样**——`e2e/conftest.py` 里我们写了自动起服务的夹具（见 5.4），所以云端不需要任何额外操作。脚本"本地能跑，CI 就能跑"，这就是好配置的价值。

### 5.3.5 流水线的三种常见玩法（理解概念即可）

| 玩法 | 触发方式 | 干什么 |
|------|---------|--------|
| **push 触发**（你刚配的） | `on: [push]` | 每次提交都全量回归，坏了立刻知道是哪次提交弄坏的 |
| **PR 门禁** | `on: [pull_request]` | 有人发起合并请求时自动跑，**不绿不许合并**——团队质量门禁 |
| **夜间回归（Nightly）** | `on: schedule`（定时） | 每晚定时跑全套，第二天早上看报告 |

再配一枚**徽章（badge）**——README 顶部那个小图标：仓库页 Actions 里复制徽章的 Markdown 代码贴进 README，就能实时显示"最近一次流水线是绿是红"。现在，你已经凑齐了 Day1 参观成熟项目时看到的三件套：**脚本 + 流水线 + 徽章**。

## 5.4 让 pytest 自动起服务（30 min）

到现在为止，每次跑测试都要手动开一个 `python -m http.server 3000` 终端。用 pytest 夹具把它自动化——新建 `e2e/conftest.py`（conftest.py 是 pytest 的约定文件，里面的夹具对所有用例自动生效）：

```python
# e2e/conftest.py
import subprocess
import time
import urllib.request
from pathlib import Path

import pytest

PROJECT_ROOT = Path(__file__).resolve().parent.parent   # e2e/ 的上一级 = 项目根目录


@pytest.fixture(scope="session", autouse=True)
def static_server():
    """整场测试开始前自动启动本地静态服务器，结束后自动关闭"""
    proc = subprocess.Popen(
        ["python", "-m", "http.server", "3000"],
        cwd=str(PROJECT_ROOT),
    )
    for _ in range(30):                                  # 最多等 15 秒直到服务就绪
        try:
            urllib.request.urlopen("http://localhost:3000/index.html")
            break
        except Exception:
            time.sleep(0.5)
    yield                                                # ---- yield 之前是"准备"，之后是"清理" ----
    proc.terminate()
```

三个参数的人话解释：

- `scope="session"`：整场测试只起一次服务，不是每条用例都起一个
- `autouse=True`：不用在用例里声明，自动生效
- `yield` 前后：前面是**准备**（起服务），后面是**清理**（关服务）——保证不留垃圾

现在一条命令全包：起服务 → 跑测试 → 关服务：

```powershell
pytest e2e
```

本地从此不需要手动维护那个 `http.server` 终端，CI 云端也同样靠它——一处配置，两边通用。

## 5.5 Page Object 模式（20 min，知道即可）

现有写法的问题：`.book-card`、`.status` 这些定位器散落在每个用例里，页面一改版就要全局搜索替换。

## 附录 B：常见问题

**Q：定位不到元素怎么办？**
按顺序排查：① F12 确认元素真实存在、class 没写错；② 是不是在 iframe/新窗口里；③ 是不是检查跑得比页面渲染快——但不要加 sleep，确认用的是 expect 的自动等待；④ 打开 trace 看那一刻页面长什么样。

**Q：跑 `pytest e2e` 报 "Cannot navigate to invalid URL"？**
没读到 `e2e/pytest.ini` 里的 base-url。检查是否**在项目根目录**执行、且带了 `e2e` 目录参数（`pytest e2e`），而不是进到别的目录裸跑。

**Q：UI 自动化用例为什么老是"飘"（时好时坏）？**
三大根源：等待靠 sleep（→ 改自动等待）、定位器脆弱（→ 改按角色/稳定 class 定位）、用例互相依赖（→ 各自独立准备环境）。Day3、Day4 就是在系统性预防这三点。

**Q：CI 流水线红了，但我本地跑是绿的？**
最常见原因：① 云端环境和你本地不一样（Python 版本、依赖没写进 requirements.txt）——CI 每次都是全新电脑，专治"只有我电脑能跑"；② CI 上路径、端口和你本地写死的不一致。看 Actions 里的日志，报错会精确到步骤。

**Q：本项目没有按钮、没有表单，学的这些到真实项目够用吗？**
够。定位、断言、等待、组织、回归、挂 CI——这六件事是所有自动化工程的骨架；真实项目多了点击按钮、填表单（`page.fill()`）、处理弹窗等动作，框架语法现查即可，骨架不变。
